### Why the misses are (mostly) not recoverable

- `case_04` (account_004), `case_18` (audit_record_6645), `case_20` (audit_record_5569): the gold plan contains a resource id that appears **nowhere** in `dataset/` (not in any evidence file or activity row), so no method can name it.
- `case_23` (account_410 vs account_7015): two deletion events with the same result are equally plausible for two cases reported in the same batch; the activity ordering carries no case information (tested: event order vs case number, requested_at, user id, email, name, hash, resource id all ~50% concordant). The pipeline picks deterministically.

### Threats to validity (read this before trusting the numbers)

- **In-sample.** The heuristics were developed while looking at these 32 cases, so the figures above are optimistic for the hidden 518. To limit overfitting every rule was kept to a general, explainable principle (anchor file, per-category resource, status/result mirroring, absence by omission) rather than a case-specific fix, and the rules were also checked for self-consistency on all 518 unlabelled requests (see section 3).
- **Ambiguity is inherent.** Identifier-free records (404 accounts, anonymised analytics profiles) can only be attributed through the deletion-worker activity batch. Where elimination cannot settle it, the pipeline keeps a best guess so that step numbering stays aligned; expect those steps to be right roughly half the time.

## 5. Failures found and improvements made

Every row is a real failure found while building the system (sample metrics = the 32 labelled requests; "S/P/R/F1" = status accuracy / step precision / step recall / step F1). Numbers are the ones observed at that point of development.

### Metric history on the labelled samples

| Version | What changed | S | P | R | F1 |
| --- | --- | --- | --- | --- | --- |
| v0 | Link records to the person by identifier; take the newest observation anywhere; absence by omission from any snapshot that enumerates the category | 84.4% | 99.3% | 74.6% | 85.2% |
| v1 | **Anchor file** (latest evidence that mentions the person) is the source of truth; accounts attributed through the deletion-worker batch | 87.5% | 99.4% | 82.4% | 90.1% |
| v2 | Secondary-identifier + restore-candidate events, fallback for resources the anchor does not list, tie-break rule | 93.8% | 98.9% | 90.7% | 94.6% |
| v3 | Two-tier activity windows; anchored fallback to record-level observations | 96.9% | 98.9% | 95.9% | 97.4% |
| v4 | Anchor-scoped resource set, one resource per data category, stale-observation cut-off | 96.9% | 99.5% | 96.4% | 97.9% |
| v5 | Visual-evidence facts + data-catalog links (screenshots/PDFs), catalog-aware anchoring | **100%** | **99.5%** | **97.9%** | **98.7%** |

| --- | --- | --- | --- | --- |
